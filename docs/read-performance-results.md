# 差分readの性能改善結果

2026-09-12、macOS / Node v25.1.0 / 同梱Codex 0.153.4 / codex-steer 0.10.0で計測した。対象は`01a070ad-2740-7382-8fd8-e9f6f013f92d`。42ターン、14,311項目の保存済みタスクで、計測中の状態は`notLoaded`。再開・送信・Desktop再起動は行っていない。

## 結果

差分readは50回すべて1秒未満。各回で新しいCLIプロセスを起動し、接続、取得、JSON出力、終了までを測った。既に起動しているApp Serverを利用しており、サーバー起動時間やディスクキャッシュの消去は含まない。

| 対象 | 改善前 | 改善後 |
| --- | ---: | ---: |
| 差分0件のread | 10,509.73ms（1回） | 最大77.97ms（50回） |
| 同・中央値 | — | 59.44ms |
| 同・p95 | — | 63.44ms |
| 同・最小値 | — | 56.16ms |
| 履歴取得の受信量 | 124,466,110 bytes | 11,797 bytes |
| 新着・コマンド完了ありのread | 未計測 | 最大60.97ms（隔離環境で4回） |

改善前の初回readは3回で10,031.62〜10,251.80ms、改善後の初回readは65.66ms（1回）だった。計測値と全50試行は[集計JSON](read-performance-results.json)に保存している。タスク本文・コマンド出力・cursorは保存していない。

## 何が遅かったか

以前は`thread/read(includeTurns:true)`と`thread/turns/list(itemsView:full)`で、約62.2MBの同じ全履歴を2回取得していた。差分0件や`--limit 1`でもこの処理が必要だった。計測ではRPC取得に約10.26秒、表示用変換に約85ms、JSON出力の直列化に約0.1msかかっていた。

まず全履歴の二重取得を解消し、通常経路を項目のページ取得へ変更した。現在の差分0件では、タスクのメタデータ、42ターンの本文を含まない一覧、確認済み末尾1項目だけを取得する。受信量は約99.99%減少した。内訳の別計測では、接続を含むAPI処理が4.83msだった。これはCLI起動込みの上表とは別の指標である。

初回は最新側から表示分を読み、実行中ターンがあれば、そのターンの実行項目を探索する。cursorには本文を含めず、再取得位置とハッシュを保持する。以降は新着と追跡対象のページを再取得する。内部項目しかない大量の新着にも1回あたりのページ数を制限し、残りを`has_more`とcursorで引き継ぐ。[設計の詳細](read-performance-design.md)も参照。

## 正しさの確認

- `npm test`: 119件すべて成功。新着、出力更新、古い実行中項目の完了、表示上限1件、大量ページ、取得中の新着、空ターン、履歴の巻き戻し、cursor互換性、Monitor、送信前の鮮度確認などを検証した。
- `npm run check`: 成功。
- `npm run test:protocol`: 同梱Codexと模擬モデルの隔離環境で成功。新着3ケースとコマンド完了の差分readを、各回のCLI起動込みで1秒未満と検証した。Monitorのページ通知・無変化時の無出力・中断、`thread/revert`後のcursor拒否、承認経路なども確認した。

同梱Codex 0.153.4の隔離実行では、開始通知が来てもコマンドは履歴APIにまだ現れず、完了後に初めて現れた。全履歴APIでも同じだった。この場合、完了は新規項目の`added`になる。実行中として既に観測できた項目の更新は`updated`で届けることを単体テストで確認した。履歴反映までの時間と、read自体の処理時間は区別する必要がある。

## 適用範囲と再計測

この1秒未満の判定は、上記実タスクの50回と隔離環境の4回の差分取得についての実測結果である。OSの停止やサーバー負荷を含めた、あらゆる環境での応答期限を保証するものではない。初回の巨大な実行中ターン探索、古い形式のタスク、明示した`--full-history`には全取得が必要になる場合があり、この性能基準の対象外とする。

通常の確認範囲は`history_scope:"tail-and-tracked-items"`。過去全文の書き換えを照合する場合は`--full-history`を使う。旧v1 cursorの継続にもこのオプションが必要。高速方式へ切り替える際は、`--since`なしのreadで現状をレビューし、新しいv2 cursorを保持する。`has_more:true`なら`changed:false`でも続きを読み、読み終えてから判断する。

```sh
npm run benchmark:read -- <thread-id> --samples 50 --max-ms 1000 --output /private/tmp/read-benchmark.json
```

ベンチマークは読み取り専用。各試行の時間・件数を表示し、差分readが1回でも閾値以上なら終了コード1を返す。初回readは別枠で記録する。判定には丸める前の時間を使う。
