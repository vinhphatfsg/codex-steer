# ステアリング補助機能の設計と完了条件

2026-09-12。目標は、別AIが観測・判断・指示・検証を行うための情報をCLIから扱えるようにすること。helpには日本語の使い所、出力の意味、例、制約を記載する。既存の生テキスト送信、UUID/URL、標準入力、JSON形式、明示的なUI方式を維持する。

## 機能別の実装順序

1. **状態・差分の観測**: `status/read/watch`。公開履歴から発言・コマンド・ファイル変更を抽出する。cursorは対象ID・観測位置・更新中項目・履歴ハッシュを保持し、更新中コマンドの完了も返す。履歴の巻き戻しは明示的に拒否。watchは時間制限付きの読み取りポーリングとし、購読や承認所有者を変更しない。
2. **送信追跡**: 送信前にclient_message_idを永続保存し、受付結果と受信履歴を照合する。未確認の配送は再送しない。対応状況は明示的な記録と根拠で扱い、後続発言だけで「反映済み」にしない。
3. **指示種別・根拠・鮮度**: 送信者、decision/review/hypothesis/suggestion、根拠ファイル/URLを指定可能にする。観測cursor以降のユーザー入力・ターン変更と根拠ファイルの変更を送信前に検出する。decisionという自己申告は新しい承認を意味しない。
4. **訂正・撤回**: ID指定の置換と撤回を送信し、有効な指示を一覧にする。受付不明の置換で旧指示を確定撤回せず、保留として表示する。元履歴は削除しない。
5. **検証チェックポイント**: 明示的な入力パス集合をスナップショットし、実行結果・成果物と結び付ける。実行中の入力変更や成果物変更を検知する。成功はコマンドの終了コードであり、試験の十分性や採用可否は別判断とする。
6. **共有リソース**: 同じCODEX_HOME内で名前付き期限付きリースを共有する。画面/Unity/Gitなどの協調用であり、参加しないプロセスを停止しない。画面の許可条件はユーザーが決めた記録として保持し、入力アイドルだけで許可を生成しない。
7. **Claude Code Monitor**: `watch --stream`は中断まで、変化ごとにJSONを1行出力する。初回と無変化時は無出力。cursorを使って未取得ページを順番に渡し、出力先の処理を待ってから次へ進む。切断や履歴の不整合で終了し、自動的な基準変更や再接続はしない。

各機能のコード・help・テスト・利用例を1コミットにまとめる。ユーザーの実タスクへの試験送信やDesktopの再起動は行わず、模擬サーバーと同梱CLIの隔離テストで検証する。

追加のユーザー情報: 補助AIはClaude Codeで、Monitorを使ってログ更新を受け取っている。既存のMonitor通知後にreadを呼べるようにし、直接Monitorへ渡すための変化時のみ出力するJSON Lines形式も独立した機能コミットで追加する。判断と送信はClaude Codeに任せ、監視出力から自動で送信しない。

## 検証

- 既存64テストを基準にする（ソケット待受けが許可された環境でPASS）。
- cursorの新着/更新/ページング/別タスク拒否/巻き戻し、監視のタイムアウトと接続終了を確認。
- 送信前後の障害・重複・結果不明、記録の原子更新、置換の確定条件を確認。
- 根拠変更、検証中の編集、リソース競合と期限切れを実ファイル・子プロセスで確認。
- CLI helpを各コマンドから呼び、JSON helpも確認する。
- 同梱CLIの実プロトコルで既存送信・承認・質問経路への非干渉を確認。

## 保存と限界

指示・検証・リースの記録はCODEX_HOME配下の専用ディレクトリに保存する。ファイルは0600、ディレクトリは0700とし、シンボリックリンクや不適切な所有者は拒否する。観測は公開項目のみを抽出し、内部推論を含めない。cursorは整合性確認用で認証情報ではない。

送信前の根拠確認とApp Serverへの送信は別操作であり、両者を原子的には固定できない。検証中のファイル変更を確実に避けたい場合は、固定チェックアウトまたは参加者間のリースを使う。
